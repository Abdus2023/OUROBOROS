# M1.23 — Authoritative Recovery-Quorum Integration

## Status

Normative design and implementation boundary.

## Purpose

The recovery-of-recovery quorum is an externally provisioned root at genesis.
M1.23 gives that quorum an authenticated lifecycle and makes that lifecycle
part of authoritative replay rather than an advisory side channel.

## State machine

```text
External quorum genesis
        |
        v
   Quorum epoch N
        |
        | N-of-M authenticated lifecycle statement
        v
   Quorum epoch N+1
        |
        +--> signer rotation
        +--> signer revocation
        +--> threshold change
```

A lifecycle statement is authorized by the quorum current at the exact journal
position where it occurs. The new quorum becomes effective only for subsequent
events.

## Replay invariant

Authoritative replay processes these authority-changing events in one ordered
stream:

1. recovery-quorum lifecycle
2. recovery-of-recovery / break-glass root replacement
3. recovery-root rotation
4. ordinary trust transition
5. emergency trust recovery

The implementation must never first reconstruct a final quorum and then use it
to validate historical events. Doing so would permit a later quorum change to
retroactively authorize an earlier event.

## Key lifecycle invariants

- Genesis quorum is external and cannot be manufactured by repository state.
- Every lifecycle statement binds the exact prior quorum epoch.
- Authorization threshold is evaluated against the pre-transition quorum.
- A resulting quorum must have `1 <= threshold <= membership`.
- Signer replacement requires fresh identifier and fresh key material.
- A removed signer cannot authorize later events.
- Historical signer identifiers are never reusable during replay.
- Duplicate lifecycle bindings are rejected.
- Lifecycle events are never run-, action-, or generation-scoped.
- A malformed or unauthenticated lifecycle event fails closed.
- Durable authorization uses the journal's atomic checked-append boundary.

## Checkpoint interaction

The recovery quorum is a meta-authority for replacing the emergency recovery
root; it is not the signer authority for ordinary trust checkpoints. Therefore
a quorum-only lifecycle transition does **not** by itself change the normal
`TrustStore` digest bound into a current checkpoint.

However, any subsequent break-glass recovery that changes the normal trust
state changes the reconstructed trust-state digest and requires a new current
checkpoint. This preserves separation between:

```text
normal trust checkpoint authority
        !=
recovery-of-recovery meta-authority
```

No repository-local quorum file is sufficient to establish either root.

## Failure rule

If authoritative replay encounters a quorum lifecycle event but no external
quorum was supplied, recovery is rejected. If the event is invalid, stale,
replayed, incorrectly scoped, or signed by a signer no longer in the current
quorum, recovery is rejected.

> The repository may record the evolution of the recovery quorum, but it can
> never create the external quorum that gives that evolution its authority.
