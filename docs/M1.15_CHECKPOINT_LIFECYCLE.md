# M1.15 — Trust Checkpoint Lifecycle

## Status

Normative conformance slice: checkpoint freshness across trust-state, journal-head, and repository-generation changes.

## Invariant

A current checkpoint is valid only for the exact externally rooted trust state, journal head, trust epoch, and repository generation that it signs.

Therefore:

```text
checkpoint(epoch N, head H, generation G, state S)
                     |
             authenticated transition
                     v
          state S' / epoch N+1 / head H'
                     |
                     v
             previous checkpoint
                  is stale
                     |
                     v
              new checkpoint
                     |
                     v
       signed by new ACTIVE authority
```

## Normative rules

1. The current trust state is reconstructed from the externally provisioned genesis trust store and the ordered authenticated journal transitions.
2. A current checkpoint MUST bind the exact current journal sequence and digest.
3. A current checkpoint MUST bind the exact repository generation.
4. A current checkpoint MUST bind the canonical digest of the reconstructed trust state.
5. A trust rotation changes the active key and trust epoch; the pre-rotation checkpoint therefore cannot authenticate the post-rotation journal.
6. A new current checkpoint after rotation MUST be signed by the new ACTIVE key.
7. A retired key may remain useful for explicitly historical verification where permitted by the trust lifecycle rules, but it cannot authorize the current state.
8. A checkpoint whose generation differs from the current generation cannot authorize the current repository.
9. Checkpoint issuance MUST NOT append an issuance event to the journal being checkpointed, because that would advance the signed journal head and immediately make the checkpoint stale.
10. The repository cannot create a new root of trust merely by modifying checkpoint or trust-store files.

## Lifecycle matrix

| Repository state | Old checkpoint | Required current checkpoint |
|---|---|---|
| Before rotation | CURRENT | Existing checkpoint |
| After authenticated rotation | STALE | Re-issue at new epoch/head/state |
| After new checkpoint | CURRENT | New active-key checkpoint |
| Different repository generation | INVALID for current authority | Checkpoint for current generation |
| Journal head changed by any later event | STALE | Checkpoint covering the new head |

## Conformance coverage

`ouroboros/M0/tests/test_m1_15_checkpoint_lifecycle.py` verifies:

- a newly issued checkpoint authenticates the current state;
- authenticated rotation invalidates the previous checkpoint through journal-head mismatch;
- the old active private key cannot issue the post-rotation checkpoint;
- the new active key can issue the replacement checkpoint;
- generation changes prevent reuse of an older checkpoint.

## Security consequence

Checkpoint freshness is derived from immutable bindings rather than a mutable revocation list. Any trust-state transition or journal mutation necessarily changes the state that a current checkpoint must describe.
