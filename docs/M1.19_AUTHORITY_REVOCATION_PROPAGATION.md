# M1.19 — Authority Revocation Propagation

## Status

M1.19 defines the propagation boundary from authenticated trust lifecycle state to checkpoint authority decisions.

## Normative principle

> A checkpoint's historical cryptographic validity never overrides the current authenticated trust state.

A checkpoint is current only if its signer remains authorized in the trust state reconstructed from the externally provisioned genesis root and the complete ordered journal.

## Propagation chain

```text
External Genesis Root
        ↓
Ordered Journal
        ↓
Authenticated Trust Replay
        ↓
Current TrustStore
        ↓
Checkpoint Signature + Binding Verification
        ↓
Checkpoint Authority Classification
        ↓
CURRENT / STALE / REVOKED / INVALID / ABSENT
        ↓
Promotion / Bootstrap Decision
```

## Revocation

When an authenticated transition changes a historical signing key to `REVOKED`, every checkpoint signed by that key loses current authority immediately. The checkpoint file itself does not need to change. Its authority is evaluated against the newly reconstructed trust state.

`REVOKED` is terminal for that key. Restoring an old checkpoint file, rewriting its metadata, changing its filename, or changing repository-local trust material cannot restore authority.

## Rotation and supersession

Rotation changes the active key and advances the trust epoch. A pre-rotation checkpoint therefore cannot authenticate the post-rotation journal head or reconstructed trust-state digest. It is `STALE` unless its signer is additionally revoked, in which case `REVOKED` is the stronger state.

A new checkpoint must be issued by the new active key and must bind the new journal head, generation, epoch, and trust-state digest.

## Emergency active-key compromise

The current lifecycle intentionally does not permit the active key to revoke itself. Therefore repository-local data cannot solve compromise of the sole active authority. Emergency recovery requires a separately authenticated, externally provisioned recovery mechanism. Until such a mechanism is authenticated, authoritative bootstrap and promotion MUST fail closed rather than infer replacement authority from repository state.

## Cached checkpoints

Cached or redundant checkpoint copies are availability mechanisms only. They do not preserve authority across trust-state changes. Every candidate must be independently authenticated against the current external root, current journal, current generation, and reconstructed trust state.

## Decision table

| Condition | Authority state | Current use |
|---|---|---|
| Missing artifact | `ABSENT` | Deny |
| Malformed/unverifiable artifact | `INVALID` | Deny |
| Valid but old generation/head/state | `STALE` | Deny |
| Signer explicitly revoked | `REVOKED` | Deny |
| All current bindings and signer authorization hold | `CURRENT` | Allow |

## Security invariants

1. Revocation is evaluated from authenticated trust history.
2. Revoked signers can never regain current authority through checkpoint restoration.
3. Checkpoint metadata never creates trust.
4. Repository-local files cannot manufacture emergency replacement authority.
5. Cached checkpoints cannot bypass current trust-state evaluation.
6. Non-current classifications are fail-closed at authorization boundaries.
7. Rotation requires re-issuance of the current checkpoint.
