# OUROBOROS M1.12 — Trust Replay Integrity

## Normative purpose

M1.12 defines trust-state recovery as a deterministic, monotonic replay of authenticated lifecycle statements from an externally provisioned genesis root.

The repository is never permitted to manufacture the initial trust root.

## Replay invariants

1. **External root** — recovery begins from the supplied genesis `TrustStore`; serialized repository state cannot replace it.
2. **Journal order** — lifecycle statements are applied in durable journal order. A later-epoch statement cannot be accepted before its predecessor establishes that epoch.
3. **Authenticated transition** — every transition must be signed by the current ACTIVE key and satisfy the exact operation/epoch constraints.
4. **No duplicate authorization** — a lifecycle binding digest may occur only once during a recovery.
5. **Monotonic epochs** — `ROTATE` advances exactly one epoch; `REVOKE` preserves the epoch.
6. **Revocation permanence** — a REVOKED key cannot become ACTIVE again through replay.
7. **Single active authority** — every reconstructed state has exactly one ACTIVE key whose epoch equals the store epoch.
8. **Determinism** — replaying the same ordered event sequence from the same external root produces the same canonical trust state.
9. **No scoped trust authority** — trust lifecycle events cannot be attached to a run, action, or repository generation.
10. **Fail closed** — malformed, reordered, forged, stale, duplicate, or contradictory transitions abort recovery rather than being ignored.

## State transition vocabulary

```text
ROTATE(k[n] → k[n+1])
    signer = ACTIVE k[n]
    from_epoch = n
    to_epoch   = n + 1
    k[n]       = RETIRED
    k[n+1]     = ACTIVE

REVOKE(k[x])
    signer     = current ACTIVE
    from_epoch = current epoch
    to_epoch   = current epoch
    k[x]       = REVOKED
```

There is no legal transition from `REVOKED` back to `ACTIVE`, and no legal transition that skips an epoch.

## Recovery equivalence

Given external root `T₀` and ordered authenticated transition sequence `E`:

```text
recover(E, T₀) = Tₙ
```

The result is authoritative only because `T₀` was externally provisioned and each transition was independently authenticated. The repository supplies the evidence sequence; it does not supply the root.

## Security boundary

```text
EXTERNAL GENESIS TRUST ROOT
          │
          ▼
   ordered journal events
          │
          ▼
 authenticated replay
          │
          ▼
 canonical TrustStore
          │
          ├── checkpoint verification
          ├── current-generation authentication
          └── promotion authority
```

An attacker who can rewrite repository state may attempt to rewrite the replay history as well; therefore replay integrity remains subordinate to the externally anchored journal/checkpoint boundary established in M1.5–M1.9.

## Conformance coverage

M1.12 tests cover deterministic replay, out-of-order transitions, duplicate/replayed authorization, revocation permanence, and rejection of repository-derived trust roots.
