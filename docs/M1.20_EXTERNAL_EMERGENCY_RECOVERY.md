# M1.20 — External Emergency Recovery Authority

## Status

**Normative.** M1.20 adds a second, externally provisioned authority path for the specific case in which the current ACTIVE trust key is compromised.

## Problem

Normal trust lifecycle deliberately requires the current ACTIVE key to authorize rotation and rejects revocation of that same ACTIVE key. That prevents a repository-local actor from inventing a self-authorized replacement. It also means an actually compromised ACTIVE key cannot be recovered by ordinary lifecycle operations.

M1.20 resolves this without making the repository a root of trust.

```text
External Emergency Root
        │
        │ signs
        ▼
Emergency Recovery Statement
        │
        ├── expected ACTIVE key
        ├── expected trust epoch
        ├── fresh replacement key
        └── replacement epoch
        │
        ▼
Ordered Journal
        │
        ▼
Authenticated Trust Replay
        │
        ├── compromised key → REVOKED
        └── replacement key → ACTIVE
        │
        ▼
Current Checkpoint Re-issuance
```

## External recovery root

The emergency recovery public key is provisioned outside repository-controlled state. Its private key is never serialized into the repository, trust store, journal, checkpoint, or recovery statement.

A recovery statement is accepted only when:

1. its `recovery_key_id` matches the externally supplied recovery authority;
2. its signature verifies under that external public key;
3. its `expected_active_key_id` equals the reconstructed current ACTIVE key;
4. `from_epoch` equals the reconstructed current trust epoch;
5. `to_epoch` is exactly `from_epoch + 1`;
6. the replacement key ID is fresh;
7. replacement key material differs from the compromised key;
8. the event is not run-scoped.

The repository cannot satisfy these conditions by editing its own recovery material because the recovery signature is verified against an external public root.

## Atomic trust transition

Emergency recovery is one logical transition. The compromised ACTIVE key becomes `REVOKED` and the fresh replacement becomes `ACTIVE` at the next epoch. There is no intermediate state in which two ACTIVE keys exist.

`REVOKED` is intentional rather than `RETIRED`: compromise means the old key must not regain current or historical authority through ordinary checkpoint verification.

## Replay and rollback resistance

The signed statement binds the expected active key and exact source epoch. Consequently:

- replay after successful recovery fails because the expected ACTIVE key and epoch no longer match;
- replacement key ID reuse fails;
- duplicate durable authorization fails;
- malformed or forged statements fail closed;
- run-scoped recovery events are rejected;
- a journal containing an emergency event cannot be replayed without the externally provisioned recovery root.

The recovery root does **not** use a repository-local counter as authority. The trust epoch reconstructed from the externally rooted journal is the state precondition for application.

## Checkpoint consequences

An emergency recovery changes the trust state and advances the journal. Therefore every checkpoint issued before recovery is stale or revoked according to its signer:

```text
checkpoint signed by compromised key
        ↓
Emergency replacement
        ↓
compromised key = REVOKED
        ↓
old checkpoint = REVOKED
```

A new checkpoint must be issued after recovery. It must be signed by the new ACTIVE key and must bind:

- the new journal head;
- the current repository generation;
- the reconstructed post-recovery trust state.

No recovery event is appended after checkpoint signing during issuance; otherwise the newly issued checkpoint would immediately become stale.

## Bootstrap and promotion boundary

Authoritative bootstrap and promotion require the recovery authority whenever the journal contains an emergency recovery event. Supplying only the original genesis trust store and checkpoint is insufficient.

```text
No recovery authority
        +
Emergency event present
        ↓
FAIL CLOSED
```

After recovery, authority is not restored merely because a replacement checkpoint file exists. The checkpoint must authenticate against the externally rooted reconstructed trust state and the exact current journal and generation.

## Failure matrix

| Condition | Result |
|---|---|
| Valid external recovery statement | Apply replacement |
| Forged recovery signature | Reject |
| Wrong recovery root | Reject |
| Wrong expected ACTIVE key | Reject |
| Wrong source epoch | Reject |
| Non-fresh replacement key | Reject |
| Run-scoped recovery event | Reject |
| Duplicate/replayed statement | Reject |
| Missing recovery authority | Fail closed |
| Old checkpoint after recovery | `REVOKED` / not current |
| Recovery without new checkpoint | Not authoritative |
| New valid checkpoint under replacement key | `CURRENT` |

## Security boundary

M1.20 does not claim to solve compromise of the emergency recovery root itself. That is a separate lifecycle problem and must be handled by a future externally authenticated recovery-root lifecycle. Until such a mechanism exists, compromise of the emergency root requires operational replacement of the externally provisioned root; repository-local state cannot perform that replacement authoritatively.

## Invariant

> Emergency recovery may replace a compromised ACTIVE trust key only through a separately authenticated external recovery root, and recovery never manufactures authority from repository-controlled state.
