# M1.13 — Checkpoint Continuity and Trust-State Binding

## Status

M1.13 defines the authoritative current-checkpoint binding contract.

## Normative invariant

A current checkpoint is authoritative only when one signed artifact binds all
of the following values simultaneously:

```text
trust_epoch
journal sequence
journal head digest
generation
reconstructed trust-state digest
signing key identity
```

The trust-state digest is:

```text
SHA-256(canonical_json(TrustStore.to_record()))
```

where canonical JSON uses sorted keys, compact separators, and UTF-8.

## Checkpoint versioning

M1.12's `ourob.signed-checkpoint.v1` remains a distinct legacy format.
M1.13 introduces:

```text
ourob.signed-checkpoint.v2
```

with the additional signed field:

```text
trust_state_digest
```

Authoritative current bootstrap requires v2. Legacy v1 checkpoints are not
silently upgraded and cannot satisfy the M1.13 current-authority gate.

## Verification order

The current trust boundary performs these operations:

1. Validate the complete journal hash chain.
2. Recover trust from the externally provisioned genesis store.
3. Require a v2 checkpoint.
4. Require exact current repository generation.
5. Require exact current journal sequence and head digest.
6. Recompute the canonical trust-state digest from the recovered store.
7. Require equality with the checkpoint's signed `trust_state_digest`.
8. Verify the checkpoint signature against the recovered trust store.
9. Verify the journal anchor.

This ordering prevents an individually valid checkpoint, trust store, journal,
or generation value from being recombined into a different authoritative state.

## Failure conditions

Current authentication fails closed when:

- the checkpoint is v1 or otherwise lacks the state binding;
- the checkpoint generation differs from the current repository generation;
- the checkpoint sequence differs from the current journal length;
- the checkpoint journal digest differs from the current journal head;
- the checkpoint trust-state digest differs from reconstructed state;
- the checkpoint signature is invalid;
- the signing key is unknown, retired for current use, or revoked;
- the journal is malformed, truncated, reordered, or hash-chain invalid;
- authenticated trust replay fails.

## Historical checkpoints

Historical checkpoints remain audit artifacts. They may be useful for proving
what trust state existed at an earlier epoch, but they do not authorize current
bootstrap or current promotion.

## Root-of-trust rule

The repository can carry the journal and signed lifecycle transitions, but it
cannot create the genesis trust store. M1.13 adds continuity; it does not move
the root of trust into repository-controlled state.
