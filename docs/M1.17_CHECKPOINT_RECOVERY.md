# M1.17 — Checkpoint Publication Recovery

## Status

Normative recovery protocol for interrupted or redundant external checkpoint publication.

## Problem

M1.16 makes publication crash-safe at the filesystem boundary, but an external authority may still use redundant publication slots, or a process may crash after one slot becomes stale and before the replacement is published. Recovery must therefore answer one question only:

> Which published checkpoint, if any, authenticates the current repository?

It MUST NOT answer that question using filename order, modification time, sequence alone, or repository-local metadata.

## Recovery protocol

```text
candidate files
      ↓
structural validation
      ↓
external genesis trust root
      ↓
ordered journal replay
      ↓
current journal head
      ↓
current repository generation
      ↓
trust-state-bound checkpoint verification
      ↓
CURRENT / STALE / INVALID / ABSENT
      ↓
exactly one authenticated checkpoint
```

## Normative invariants

1. Every candidate is untrusted input until independently authenticated.
2. `CURRENT` requires successful current-repository authentication through the external trust boundary.
3. A candidate with a stale journal sequence/digest is `STALE`, not a usable fallback authority.
4. A generation mismatch is `STALE` for current-authority recovery.
5. Malformed, truncated, empty, or schema-invalid files are `INVALID`.
6. Missing files are `ABSENT`.
7. Recovery MUST fail closed when no candidate is current.
8. Recovery MUST fail closed when multiple distinct candidates authenticate as current.
9. Recovery MUST NOT select a candidate by path, mtime, lexical order, or apparent recency.
10. Recovery MUST NOT mutate the external genesis trust root.
11. Recovery MUST NOT modify the journal.
12. A pre-rotation checkpoint cannot become current again after an authenticated rotation because its journal head and trust-state binding no longer match.
13. Redundant slots provide availability only; they do not weaken cryptographic or generation-bound freshness requirements.

## Candidate vocabulary

| Status | Meaning | Usable for current authority? |
|---|---|---|
| `ABSENT` | File does not exist | No |
| `INVALID` | File cannot be structurally validated | No |
| `STALE` | Structurally valid but fails current trust-bound authentication | No |
| `CURRENT` | Fully authenticates against current external authority and repository | Yes |

## Crash and rotation behavior

```text
Checkpoint C0 published
        ↓
Journal advances
        ↓
C0 = STALE
        ↓
Publish C1
        ↓
C1 = CURRENT
```

If publication of `C1` is interrupted, recovery may still observe `C0`, but it MUST report that there is no current checkpoint. It MUST NOT silently authorize using `C0`.

With redundant slots:

```text
slot A = stale C0
slot B = current C1
        ↓
recover_current_checkpoint(A, B)
        ↓
select C1
```

If both slots contain the same authenticated current checkpoint, they are equivalent redundant copies. If distinct checkpoints both claim current authority, recovery fails closed rather than inventing precedence.

## Security boundary

The recovery layer is deliberately downstream of the external trust boundary:

```text
Repository files
     │
     ▼
Candidate parsing ─────────────┐
                              │
External genesis root ────────┼──► authenticate_current_repository()
                              │
Current journal ──────────────┘
                              ↓
                         CURRENT / reject
```

Thus repository-controlled checkpoint files can improve availability, but cannot create authority. A repository compromise can at most cause candidates to become invalid or stale; it cannot turn an unauthenticated artifact into the current trust root.

## Relationship to M1.16

M1.16 guarantees atomic filesystem publication of an individual checkpoint. M1.17 defines how an external authority safely recovers from incomplete publication or redundant slots.

```text
M1.14  issuance correctness
M1.15  checkpoint freshness
M1.16  crash-safe publication
M1.17  crash/redundant-slot recovery
```

Together these establish a fail-closed publication lifecycle: **issue → publish → authenticate → recover, never infer**.
